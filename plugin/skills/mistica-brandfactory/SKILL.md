# Mística component documentation for Brand Factory

Generates the content added to a Mística component's page in Brand Factory, based on its code (`mistica-web`) or its `.md` specs, translated into design language.

## Workflow

### 1. Choose the source and the output format

Ask the user, in a single message:

- **Component name.**
- **Source of truth**, offering both options and **recommending A**:
  - **A — Code (recommended).** Documents what is in production in `mistica-web`. Only available if the component is already implemented.
  - **B — `.md` specs.** For components not yet implemented, or when the user prefers the design specs.
- **Output format:** `.docx` or `.md` (use the `anthropic-skills:docx` skill if available for `.docx`).

If the user already gave any of this, do not ask again. If they chose A but the component cannot be found in the repo, tell them and offer B.

**Path A — component in code.** Read the component source, not only its name:
- Main file: `src/<component>.tsx` and its `.css.ts`. The file name may differ from the component name or be split across several files; search the repo before concluding that it does not exist.
- Stories: `src/__stories__/<component>-story.tsx` (for example `src/__stories__/button-story.tsx`). They show which prop combinations the team considers representative.
- GitHub connector available → read them from the `Telefonica/mistica-web` repo.
- No connector → public repo: `https://raw.githubusercontent.com/Telefonica/mistica-web/master/src/<component>.tsx`.
- If the component does not appear, ask before inventing anything and offer path B.

**Path B — no code, with `.md` specs.** The `.md` is generated by `scripts/figma-spec` (header `<!-- Generated by scripts/figma-spec -->`, script from the `mistica-design` repo) and is expected at `specs/<component>.md` in that repo. Ask the user to paste or upload it.
- **Pending: location of the specs.** Today the `.md` files live in the `mistica-design` repo, branch `aweell-generate-figma-specs`. It is still to be decided where they will be hosted permanently, so the branch or path may change. If the branch no longer exists, warn the user and ask them for the file instead of guessing.
- It is a **temporary** source: it reflects design intent, not implementation. State this in the draft (step 5).
- Omit pixels, measurement tables and token names (`backgroundSelectedBrandPressed`, etc.).
- Referenced figures (`figures/*.png`) are input for understanding the component, never final content.
- If you receive `.md` specs and partial code together, flag the possible divergence and ask which to follow.
- Before documenting, state the date of the `.md`'s last update. If the GitHub connector is available, get the date of the last commit that touches the `.md` in the specs branch. Include that date in the draft. Keeping the `.md` up to date is the responsibility of the author of the component's specs in Figma.

Do not proceed without reading the full source.

### 2. Align with sibling pages

If the user provides pages of components from the same family, read them so the new content fits without copying them. If none are provided, rely on step 3 (style).

**Brand Factory content is in English.** Always write in English, even if the user writes in another language.

### 3. Write the content

**Style.** Follow the Brand Factory hierarchy: main heading (component name) with its description; then titles for sections, subtitles for subsections, and body text for the rest. **No static images:** use the `.md` figures only as input; the final content is interactive embeds.

**Target length: approximately 400–700 words** (excluding closing blocks). If it clearly exceeds this, tell the user and ask whether they want to simplify the content.

**Group and prune.** Do not translate the `.md` section by section: group content into a few sections. Omit behaviour the component handles automatically and that the designer does not configure. When in doubt, ask the user what to prune.

**Optional sections.** Include a section only if it adds real value for that component. Relative order when present:

1. **Title and description** (always) — main heading with the component name and a one- or two-sentence description, without a title of its own. If there is a relevant restriction (e.g., "Web-only component."), put it in italics before the description.

2. **Interactive Demo (Playroom)** — visual embed that the user inserts into Brand Factory. To generate the snippet, tell the user they can use the external skill `mistica-web:mistica-playroom`. Once the snippet is generated in Playroom, the user must paste the link into Brand Factory (form: `https://mistica-web.vercel.app/playroom-desktop/preview/#?code=<lz-string>`; check the exact format against an existing Brand Factory page).
   In **path B**, leave a placeholder ("Interactive demo — pending component implementation") and tell the user they can prepare the snippet in advance, but it will not render until the component is implemented.

3. **Typology** (title) — ONLY if the component has named variants. Optional props without names are not Typology. Format: `**[Variant name]** — [one sentence]`.

4. **Anatomy** (title) — ONLY if there are named parts a designer needs to distinguish. Flat list with `(required)` / `(optional)` in that exact format. Source: code in path A, Anatomy section of the `.md` in path B.

5. **Usage** (title) — ONLY if there is something non-obvious. Bullets "Use [X] when/for…" plus "Consider using [Y] instead if:" when there is an alternative. If the component is self-explanatory, omit it.

6. **Accessibility** (title) — ONLY what the designer must decide or can configure. Omit what the component handles automatically. Translate into design language; no raw ARIA attributes.

7. **Custom sections** (title) — the component may have its own sections beyond the ones above, for example: Sizing, Common elements, Content, Slot.

8. **Implementation** and **Additional info** (always) — fixed blocks at the end that the user copies from an existing Brand Factory page. Do not write them: add a note reminding the user to paste them.

### 4. Translate, don't copy, the source

Never paste TypeScript types, prop names or implementation jargon. `secondaryButton?: ButtonProps` → "the component supports an optional secondary button". Purely technical props (event handlers, `dataAttributes`, tracking) → ignore them. Same rule for the path B `.md`: "width 240px" → "the component has a default width that can be overridden".

### 5. Review and deliver

Deliver the content as a **draft for review**, in the format chosen in step 1.

State the path used. In **path B**, add a visible notice at the top stating that the draft comes from the design specs `.md`, may differ from the final code implementation, and must be re-validated against `mistica-web` once the component is implemented.

At the end, tell the user to upload this content to Brand Factory manually. If the component is new, they must create the page and leave it in **draft** for review. Once reviewed, it is published.
