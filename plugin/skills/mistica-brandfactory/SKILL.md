# Mística component documentation for Brand Factory

Generates the content added to a Mística component's page in Brand Factory, based on its code (`mistica-web`) or its `.md` specs, translated into design language.

## Workflow

### 1. Locate the source of truth

Confirm the component name with the user. If it exists in `mistica-web`, use path A. If not, use path B and ask for the `.md` specs. Ask only when in doubt. The user does not provide code.

**Path A — component in code (preferred).** The skill looks up the component in `mistica-web` and documents what is in production. Read `src/<component>.tsx` and `.css.ts`:
- GitHub connector available → read them from the `Telefonica/mistica-web` repo.
- No connector → public repo: `https://raw.githubusercontent.com/Telefonica/mistica-web/master/src/<component>.tsx`. If the component does not appear, ask before inventing anything.
- Also check `src/__stories__/<component>.stories.tsx` to see which prop combinations the team considers representative.

**Path B — no code, with `.md` specs.** The `.md` is generated by `scripts/figma-spec` (header `<!-- Generated by scripts/figma-spec -->`) and lives in the `mistica-design` repo, branch `aweell-generate-figma-specs`. Ask the user to paste or upload it.
- It is a **temporary** source: it reflects design intent, not implementation. State this in the draft (step 5).
- Omit pixels, measurement tables and token names (`backgroundSelectedBrandPressed`, etc.).
- Referenced figures (`figures/*.png`) are input for understanding the component, never final content.
- If you receive `.md` specs and partial code together, flag the possible divergence and ask which to follow.
- Before documenting, state the date of the `.md`'s last update. If the GitHub connector is available, get the date of the last commit on branch `aweell-generate-figma-specs` that touches the `.md`. Include that date in the draft. Keeping the `.md` up to date is the responsibility of the author of the component's specs in Figma.

Do not proceed without reading the full source.

### 2. Align with sibling pages

If the user provides pages of components from the same family, read them so the new content fits without copying them. If none are provided, rely on step 3 (style).

**Brand Factory content is in English.** Always write in English.

### 3. Write the content

**Style.** Follow the Brand Factory hierarchy: main heading (component name) with its description; then titles for sections, subtitles for subsections, and body text for the rest. **No static images:** use the `.md` figures only as input; the final content is interactive embeds.

**Target length: 400–700 words** (excluding closing blocks). If it exceeds this, tell the user and ask whether they want to simplify the content.

**Group and prune.** Do not translate the `.md` section by section: group content into a few sections. Omit behaviour the component handles automatically and that the designer does not configure. When in doubt, ask the user what to prune.

**No section is mandatory.** Include a section only if it adds real value for that component. Relative order when present:

1. **Title and description** — main heading with the component name and a one- or two-sentence description, without a title of its own. If there is a relevant restriction (e.g., "Web-only component."), put it in italics before the description.

2. **Interactive Demo (Playroom)** — visual embed that the user inserts into Brand Factory. To generate the snippet, tell the user they can use the external skill `mistica-web:mistica-playroom`. Once the snippet is generated in Playroom, the user must paste the link into Brand Factory (form: `https://mistica-web.vercel.app/playroom-desktop/preview/#?code=<lz-string>`).
   In **path B**, leave a placeholder ("Interactive demo — pending component implementation") and tell the user they can prepare the snippet in advance, but it will not render until the component is implemented.

3. **Typology** (title) — ONLY if the component has named variants. Optional props without names are not Typology. Format: `**[Variant name]** — [one sentence]`.

4. **Anatomy** (title) — ONLY if there are named parts a designer needs to distinguish. Flat list with `(required)` / `(optional)` in that exact format. Source: code in path A, Anatomy section of the `.md` in path B.

5. **Usage** (title) — ONLY if there is something non-obvious. Bullets "Use [X] when/for…" plus "Consider using [Y] instead if:" when there is an alternative. If the component is self-explanatory, omit it.

6. **Accessibility** (title) — ONLY what the designer must decide or can configure. Omit what the component handles automatically. Translate into design language; no raw ARIA attributes.

7. **Custom sections** (title) — the component may have its own sections, for example: Usage, Sizing, Common elements, Content, Slot.

8. **Implementation** and **Additional info** — fixed blocks at the end that the user copies from an existing Brand Factory page.

### 4. Translate, don't copy, the source

Never paste TypeScript types, prop names or implementation jargon. `secondaryButton?: ButtonProps` → "the component supports an optional secondary button". Purely technical props (event handlers, `dataAttributes`, tracking) → ignore them. Same rule for the path B `.md`: "width 240px" → "the component has a default width that can be overridden".

### 5. Review and deliver

Deliver the content as a **draft for review**. Before generating it, ask the user which format they want: **.docx or .md**.

State the path used. In **path B**, add a visible notice at the top stating that the draft comes from the design specs `.md`, may differ from the final code implementation, and must be re-validated against `mistica-web` once the component is implemented.

At the end, tell the user to upload this content to Brand Factory manually. If the component is new, they must create the page and leave it in **draft** for review. Once reviewed, it is published.
